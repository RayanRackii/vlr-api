## 2. Exclusão de tenant (cascade)

### Problema

`DELETE /api/admin/tenants/{id}` falhava (ou ficava bloqueado) porque havia dados ligados: `Users` → `Units` / `Roles` / módulos / Rentals / etc. A exclusão “só do Tenant” não bastava.

### Solução implementada

Em `AdminTenantService.DeleteAsync`:

1. Abre transação.
2. Coleta `SupabaseAuthId` dos `Users` daquele tenant **antes** de apagar linhas.
3. Apaga em ordem (filhos antes de pais / Restrict FKs), incluindo entre outros:
   - Rentals / scheduling: `Slots`, `ReservationItems`, `Reservations`, `ScheduleTemplates`, `RentalLayoutItems`, `RentalLayouts`, `RentalPricings`, `OccupancyKinds`, `RentalAssets`
   - Work orders / PMOC / inventory: `WorkOrderTasks`, `WorkOrders`, `PlanTasks`, `MaintenancePlans`, `Assets`, `AssetCategories`
   - B2C: `OtpCodes`, `Customers`, `TenantModuleMenuItems`, `TenantRegistrationFields`, `UserInvites`
   - Identity: `Users`, `Roles`, `Units`, `TenantModules`
   - Por fim: `Tenants`
4. Commit.
5. **Depois** do commit: best-effort `DeleteUserAsync` no Supabase Auth para os auth ids coletados.

### Bug crítico descoberto no mesmo dia (tarde)

O passo 5 apagava Auth de **qualquer** membership do tenant — inclusive Platform Admins que tinham sido provisionados como `User` naquele tenant. Como Auth é **global** (um usuário Supabase ≠ uma linha `core.users` por tenant), excluir o tenant FICC **matou a conta Auth** dos Super-Admins.

Sintomas posteriores:

- JWT ainda válido no browser (sessão cacheada) com `sub = 64ed784f-fce4-44c6-a4a1-256905d5bcfa`
- `GET /auth/v1/admin/users/{esse-sub}` → **404**
- `GET /auth/v1/admin/users?filter=rayanracki@gmail.com` → **200** mas sem usuário utilizável / Find retornava null
- Logs API: `Skipping platform admin provision for …: no Supabase Auth user found.`
- `POST …/enter` → **400**

### Correção (fim do dia) — política de delete Auth

Ao excluir tenant, **só** chamar `DeleteUserAsync` se:

1. O `SupabaseAuthId` **não** é de um PlatformAdmin (e-mail na allowlist), **e**
2. O mesmo `SupabaseAuthId` **não** tem membership em **outro** tenant.

Mesma regra aplicada em `PlatformUserAdminService.DeleteAsync` (exclusão de membership pela tela `/admin/users`): remove a linha `core.users`, mas preserva Auth se for PlatformAdmin ou se ainda existir em outro tenant.

## 4. Navegação Super-Admin vs ambiente de tenant

### Problema

Com Super-Admin logado **fora** de um tenant (`app_metadata.tenant_id` ausente / modo plataforma), a sidebar ainda mostrava módulos de produto (PMOC, OS, Ativos, etc.) que não faziam sentido sem tenant ativo — ou mostravam módulos “globais” errados.

### Decisão / implementação

- Em modo plataforma (PlatformAdmin **e** não “dentro” de um tenant): nav só **Dashboard** + grupo **Super-Admin** (tenants, usuários, etc.).
- Dentro do ambiente do tenant (`isInTenantEnvironment`): nav de produto filtrada pelos **módulos ativos** do tenant.

### Filtro por módulos ativos (mesmo dia / mesma linha de trabalho)

- `GET /api/users/me` passa a expor `activeModules` (via `UserDirectoryService.LoadActiveModulesAsync` lendo `TenantModules`).
- FE (`navigation.ts`): `filterByActiveModules` — só mostra itens cujo módulo está ativo.
  - Exemplos: inventory → Ativos; rentals → config de portal/agenda; etc.
- Enquanto `activeModules` ainda não carregou, evita flash de itens errados (estado `null`).

## 5. “Abrir ambiente” — evolução do desenho

### 5.1 Discussão de produto

Perguntas do usuário:

1. Super-admins deveriam ter Admin em qualquer projeto (ex.: FICC) com um único login?
2. Dá para entrar no FICC pelo painel Super-Admin?
3. Quer UX que **não confunda**: card “Abrir ambiente” abrindo como se estivesse logado como admin.

Opinião alinhada: sim, suporte operacional com o mesmo login PlatformAdmin, sem senha por tenant.

### 5.2 Primeira implementação (DESCARTADA)

Ideia inicial (implementada e depois rejeitada):

- Abrir em **outra aba**.
- Modo suporte via header tipo `X-Support-Tenant-Id` / sessionStorage no FE.
- Middleware/API tratando header especial.

**Rejeição explícita do usuário (~15:41):** não gostou. Queria que “Abrir ambiente” **realmente** colocasse a sessão como admin daquele tenant na **mesma aba**.

### 5.3 Desenho aceito (~15:44–15:50)

Premissas:

- Só ~3 Super-Admins (`PlatformAdmin:Emails`).
- No **create** de tenant: provisionar automaticamente os 3 como memberships **Admin** naquele tenant.
- “Abrir ambiente”: mesma aba em `rolvix.com.br` (B2B), **não** redirecionar para `{subdomain}.rolvix.com.br` (B2C).
- Setar `app_metadata.tenant_id` no Auth do usuário atual + `refreshSession` no FE.
- “Voltar à plataforma”: limpa `tenant_id` do `app_metadata`.
- FICC antigo seria **recriado** pelo usuário; **não** fazer script one-shot só para o tenant legado.

Depois: único composto `(TenantId, SupabaseAuthId)`.

- Migration: `20260805185352_UserMembershipPerTenant`

- Create: `core.ix_users_tenant_id_supabase_auth_id` (unique composto)

## 7. Aceite de convite (find-or-create + senha)

### Problema

`POST /api/invites/accept` só criava Auth user. Se o e-mail **já existia** no Supabase Auth, falhava ou não atualizava a senha definida na tela `/invite`.

### Correção em `TenantUserAdminService.Accept…`

1. `FindUserIdByEmailAsync`
2. Se não existe → `CreateUserAsync(email, password)`
3. Se existe → `SetUserPasswordAsync(id, password)`
4. `UpdateUserAppMetadataAsync(tenantId)`
5. Cria/atualiza `User` + role; marca invite aceito
6. FE: após aceitar, tenta **auto sign-in** com a senha definida

Observação: após **delete** de tenant, tokens de invite antigos → 404/inválidos (esperado). Usar e-mail de convite novo.

## 9. Incidente de produção do enter (tarde) e remediação

### Evidências (logs Supabase + Railway)

```
POST /api/admin/tenants/d3dd0a78-…/enter → 400
GET  /auth/v1/admin/users/64ed784f-fce4-44c6-a4a1-256905d5bcfa → 404
GET  /auth/v1/admin/users?filter=rayanracki@gmail.com → 200
WRN  Skipping platform admin provision for vinipaulinoevangelista@gmail.com: no Supabase Auth user found.
WRN  Skipping platform admin provision for rayanracki@gmail.com: no Supabase Auth user found.
WRN  Skipping platform admin provision for leonardo.liberatti.berni@gmail.com: no Supabase Auth user found.
```

Também houve `DELETE`/`PUT` 404 no mesmo UUID — Auth id órfão.

### Causa raiz

1. Cascade delete de tenant apagou Auth dos Platform Admins.
2. Sessão JWT no browser continuava “válida” (assinatura OK até expirar) mas `sub` não existe mais no Auth.
3. Enter: Find por e-mail → null → fallback JWT `sub` → `UserExists` false → 400.
4. Provision: Find null → skip (antes da correção de recreate).

### Correções finais do dia

**A. Delete Auth seguro** (tenant delete + platform user delete) — ver §2.

**B. `ResolveOrCreateAuthUserIdAsync` em `PlatformAdminMembershipService`:**

- Find por e-mail
- Se ausente → `CreateUserAsync` com senha temporária aleatória (32 bytes Base64)
- Log warning: precisa resetar senha
- Se Create falhar (race / already exists) → Find de novo uma vez

Usado em: `ProvisionPlatformAdminsAsync`, `EnsureMembershipAsync`, `EnterTenantAsync`.

**C. Enter com sessão órfã:**

- Resolve/cria Auth pelo **e-mail**
- Garante membership + seta `tenant_id` no Auth **novo/correto**
- Se JWT `sub` ≠ auth id resolvido **ou** JWT user não existe → `InvalidOperationException` (400) com mensagem pedindo:
  - logout
  - “Esqueci a senha”
  - login de novo
  - tentar Abrir ambiente outra vez

**D. Frontend — recovery de senha (não existia no B2B):**

- `LoginPage`: botão **Esqueci a senha** → `supabase.auth.resetPasswordForEmail` com `redirectTo = {origin}/reset-password`
- Nova página `ResetPasswordPage` em `/reset-password` → `supabase.auth.updateUser({ password })`
- Rota registrada em `AppRoutes.tsx`

**E. Ops pós-deploy (runbook para o usuário):**

1. Ainda logado com JWT órfão, clicar **Abrir ambiente** uma vez (recria Auth; erro de sessão desatualizada é esperado).
2. Logout.
3. `/login` → Esqueci a senha → definir senha.
4. Login → Abrir ambiente de novo.
5. Confirmar no Supabase Auth que `https://rolvix.com.br/reset-password` está nas Redirect URLs.

Atalho: criar o user manualmente no dashboard Auth **antes** do recreate automático (se já recriou com senha aleatória, usar reset).
